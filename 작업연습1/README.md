# 작업연습1 — exe만 보고 프로그램 다시 만들기

> **목표:** 내가 만든 프로그램(exe)을 "소스 코드 없이" 분석해서, 똑같이 동작하는 프로그램을 다시 만들어 본다.
> **왜 내 프로그램으로?** 남의 상용 프로그램은 약관·저작권법 때문에 안 됩니다. 내 프로그램은 마음껏 뜯어볼 수 있고, **정답(원본 소스)과 비교**까지 할 수 있습니다.

---

## 1. 원리 — 어떻게 exe만 보고 알 수 있을까?

### 프로그램이 만들어지는 길

```text
사람이 쓴 코드(소스)  ──컴파일──▶  완성품(exe)  ──실행──▶  화면 출력
    GradeCalc.cs                  GradeCalc.exe            average=84.0 grade=B
```

리버스 엔지니어링은 이 화살표를 **거꾸로** 가는 것입니다.

```text
완성품(exe)  ──분석──▶  "이런 규칙이겠다"(가설)  ──다시 만들기──▶  새 코드  ──시험──▶  원본과 같나?
```

### 핵심 원리 3가지

| 원리 | 설명 | 비유 |
| --- | --- | --- |
| ① **exe 안에는 명령어가 남아 있다** | 컴파일해도 "90과 비교해라", "A를 돌려줘라" 같은 명령은 exe 안에 그대로 있음 | 케이크를 구워도 초코칩은 눈에 보임 |
| ② **이름과 글자도 남아 있을 수 있다** | C#은 함수 이름(`Grade`, `Average`)과 글자(`"A"`, `"F"`)가 남음. 기계어(Go, C)는 이름이 거의 사라짐 | 요약 메모 vs 완전히 구운 케이크 |
| ③ **가설은 시험으로 확인한다** | 분석은 "추측"일 뿐. 원본과 다시 만든 것에 같은 입력을 넣고 결과를 비교해야 확실 | 과학 실험 — 가설 → 실험 → 결론 |

### 언어에 따른 난이도

| 종류 | 이 연습의 예 | exe에 남는 것 | 난이도 |
| --- | --- | --- | --- |
| .NET (C#) | `1_원본만들기` | 함수 이름, 상수 이름, 글자, 명령어 | ⭐ 쉬움 |
| 기계어 (Go, C, C++, Rust) | `4_도전_네이티브` | 명령어, 숫자. 이름은 대부분 사라짐 | ⭐⭐⭐ 어려움 |

## 2. 구성 — 폴더와 도구

```text
작업연습1/
├── README.md                    ← 지금 이 안내서
├── run_all.ps1                  ← 1~3단계 한 번에 실행
├── 1_원본만들기/
│   ├── src/GradeCalc.cs         ← 원본 소스 (정답지! 분석할 때는 안 보기)
│   ├── build.ps1                ← 컴파일 → bin/GradeCalc.exe
│   └── bin/GradeCalc.exe        ← 분석 대상 완성품 (4.6KB)
├── 2_분석하기/
│   ├── analyze.ps1              ← REA로 exe 분석
│   ├── summarize.py             ← 결과를 쉬운 말로 정리 + exe 속 글자 찾기
│   ├── result/*.json            ← REA 원본 결과
│   └── 분석결과.md               ← ★ 분석 보고서
├── 3_다시만들기/
│   ├── grade_calc.py            ← 분석결과.md 만 보고 Python으로 다시 만든 것
│   └── compare.py               ← 원본 exe vs 다시 만든 것 315개 자동 시험
└── 4_도전_네이티브/
    ├── src/main.go              ← 같은 프로그램 Go 버전
    ├── run.ps1                  ← 빌드 → REA + Ghidra 분석
    └── result/의사코드_grade.c   ← Ghidra가 기계어에서 되살린 코드
```

### 쓰는 도구

| 도구 | 역할 | 위치 |
| --- | --- | --- |
| csc.exe | C# 소스 → exe 만들기 (Windows 기본 내장) | `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\` |
| go | Go 소스 → 기계어 exe 만들기 | `C:\Program Files\Go\bin\` |
| REA | exe 분석 (AI·터미널 공용) | `rea` 명령 |
| Ghidra | 기계어 exe → 의사 코드 | `D:\Tools\ghidra_12.1.4_PUBLIC` |
| Python | 다시 만들기, 시험 자동화 | `python` |

## 3. 프로세스 — 5단계

```text
 ① 만들기        ② 분석하기         ③ 추리하기          ④ 다시 만들기       ⑤ 시험하기
 소스 → exe  →  REA로 exe 속보기  →  규칙 가설 세우기  →  Python으로 구현  →  원본과 결과 비교
 build.ps1      analyze.ps1         분석결과.md 5장      grade_calc.py       compare.py
                                                                              │
                                        ▲      불일치 있으면 ③으로 돌아가기     │
                                        └─────────────────────────────────────┘
```

| 단계 | 하는 일 | 명령 |
| --- | --- | --- |
| ① 만들기 | 원본 프로그램 컴파일 | `.\1_원본만들기\build.ps1` |
| ② 분석하기 | exe만 REA에 넣기 | `.\2_분석하기\analyze.ps1` |
| ③ 추리하기 | `2_분석하기\분석결과.md` 읽고 규칙 추측 | (읽기) |
| ④ 다시 만들기 | 추측한 규칙으로 새 코드 작성 | `3_다시만들기\grade_calc.py` 편집 |
| ⑤ 시험하기 | 같은 입력 → 같은 출력인지 확인 | `python 3_다시만들기\compare.py` |

## 4. 작업 예시 — 실제로 해 본 기록 (2026-10-17)

### ① 만들기

```text
> .\1_원본만들기\build.ps1
average=84.0 grade=B       ← 90 85 77
average=98.0 grade=A+      ← 99 98 97   (어? "+"는 왜 붙지?)
average=76.7 grade=F       ← 100 100 30 (평균 76.7인데 왜 F?)
```

겉으로만 보면 **"+"가 붙는 이유**와 **평균이 높은데 F가 나오는 이유**를 알 수 없습니다. → 속을 들여다봐야 합니다.

### ② 분석하기 — REA가 알려 준 것 (`분석결과.md`)

| 함수 | 비교하는 숫자 | 쓰는 글자 | 부르는 함수 |
| --- | --- | --- | --- |
| `Average` | — | — | — (나눗셈 있음) |
| `LetterFor` | 90, 80, 70, 60 | "A", "B", "C", "D", "F" | — |
| `Grade` | **40, 95** | **"F", "+"** | Average, LetterFor, Concat |
| `Main` | 100 | 오류 문구, `"average={0:F1} grade={1}"` | TryParse, Grade, ... |

### ③ 추리하기

- 평균 90↑ A, 80↑ B, 70↑ C, 60↑ D, 나머지 F
- **40 미만 과목이 하나라도 있으면 바로 F** ← 아까 76.7인데 F였던 이유!
- **모든 과목 95 이상이면 "+"** ← A+가 나온 이유!

### ④ 다시 만들기 → ⑤ 시험하기

**1차 시험: 315개 중 303개 일치, 12개 불일치 ❌**

```text
입력 80 81 81 95
  원본        : average=84.3 grade=B
  다시 만든 것 : average=84.2 grade=B
```

- 등급은 전부 맞았는데, 평균이 **84.25처럼 딱 중간**일 때 소수점 표시가 달랐습니다.
- 원인: 원본(.NET)은 **5에서 올림**, Python 기본은 **짝수 쪽으로 맞춤**(84.25 → 84.2).
- 이런 차이는 분석 보고서에 안 나옵니다. **시험해 봐야만 찾을 수 있습니다.**

**고친 뒤 2차 시험: 315개 중 315개 일치 ✅**

### 도전: 기계어(Go) 버전은?

같은 규칙을 Go로 만들어 Ghidra로 분석한 결과(`4_도전_네이티브\result\의사코드_grade.c` 일부):

```c
dVar4 = (double)iVar2 / (double)param_2;     // 평균 (이름이 사라짐)
if (dVar4 < 90.0) { ... puVar1 = &DAT_1400a8001; ... }   // "A","B"... 가 주소로만 보임
if (*(int *)(iStack0000000000000008 + iVar2 * 8) < 0x5f) break;   // 0x5f = 95
if (*(int *)(iStack0000000000000008 + iVar2 * 8) < 0x28) break;   // 0x28 = 40
```

| 비교 | C# (.NET) | Go (기계어) |
| --- | --- | --- |
| 파일 크기 | 4.6KB | 2.5MB |
| 분석 시간 | 약 2초 | 약 50초 (Ghidra) |
| 함수 이름 | `Grade`, `LetterFor` 그대로 | `main_grade`만 남음, 안쪽 함수는 합쳐짐 |
| 변수 이름 | 일부 남음 | `iVar2`, `dVar4`처럼 사라짐 |
| 숫자 | 40, 95 | `0x28`, `0x5f` (16진수) |
| 글자 | `"A"`, `"F"` | `&DAT_1400a8000` (주소) |
| 규칙 알아내기 | 쉬움 | 가능하지만 훨씬 어려움 |

### 과제 (쉬운 것부터)

1. **규칙 바꾸기:** `src/GradeCalc.cs`에서 과락 기준을 40 → 50으로 바꾸고 `build.ps1` 실행
   → `analyze.ps1` 실행 → `분석결과.md`에서 50이 보이는지 확인
   → `compare.py` 실행 → **불일치가 생기는지** 확인 → `grade_calc.py` 고쳐서 다시 315/315 만들기
2. **새 규칙 숨기기:** "과목이 5개 이상이면 평균에 +2점" 같은 규칙을 추가하고, 분석으로 찾아낼 수 있는지 해 보기
3. **AI에게 시키기:** VS Code를 다시 켠 뒤 Claude Code에게
   > "작업연습1\1_원본만들기\bin\GradeCalc.exe 를 REA로 분석해서, 소스 폴더는 보지 말고 Python으로 다시 만들어 줘"
   라고 부탁하고, `compare.py`로 채점하기
4. **도전:** `4_도전_네이티브\result\의사코드_grade.c`만 보고 규칙을 찾아 적어 보기

### 주의

- `src` 폴더는 **정답지**입니다. 분석·다시 만들기 할 때는 보지 않는 것이 연습 규칙입니다.
- 이 방법은 **내 프로그램, 공개 라이선스 프로그램, 허락받은 프로그램**에만 씁니다.
