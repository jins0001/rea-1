2. 설명 — 왜 이게 되는가

2-1. exe 안에 남는 것

컴파일은 "사람 말 → 컴퓨터 말" 번역입니다. 번역해도 내용(규칙)은 남습니다.

원본 소스C# exe 안Go exe 안
if (s < 40) return "F";숫자 40, 글자 "F", 이름 Grade< 0x28, &DAT_1400b2cc8
Average(scores)이름 Average + 부르는 관계이름 사라짐, grade 안에 합쳐짐
"average={0:F1}"글자 그대로글자 그대로 (주소로 연결)
비유: C#은 "요약 노트", Go·C는 "구워진 케이크". 노트는 읽으면 되지만, 케이크는 맛보고 재료를 추측해야 합니다.

2-2. 겉으로는 모르는 규칙

입력출력겉으로 본 의문분석으로 찾은 답
99 98 97A+"+"는 왜?숫자 95, 글자 "+" → 전부 95↑이면 "+"
100 100 30F평균 76.7인데 왜 F?숫자 40, 바로 "F" → 과락

2-3. 분석만으로는 부족한 것

303 / 315
1차 시험 — 평균 84.25를 원본은 84.3, Python은 84.2로 표시 (반올림 방식 차이)
315 / 315
"5에서 올림"으로 고친 뒤 2차 시험

이 차이는 분석 보고서 어디에도 안 나옵니다. 시험해야만 찾을 수 있습니다.

4. 질문과 답

Q1. REA가 없으면 힘든가요?

아니요, 다른 도구로도 됩니다. 다만 REA가 있으면 편하고 AI에게 맡기기 좋습니다.

하고 싶은 일REA 없이REA를 쓰면
C# exe 분석ILSpy, dnSpy (C# 코드를 바로 보여 줌)숫자·글자·호출 관계를 JSON으로 정리
기계어 exe 분석Ghidra 화면을 직접 조작명령 한 줄로 Ghidra를 화면 없이 실행
안드로이드 앱JADX GUI같은 방식의 명령 + JSON
AI에게 맡기기도구마다 따로 연결MCP 하나로 Claude Code가 전부 사용
이 연습에서도 exe 속 글자(#US 구역)는 REA가 번호표만 줘서 Python으로 직접 읽어 연결했습니다 (summarize.py의 user_strings).

REA의 진짜 장점: ① 대상이 달라도 같은 사용법과 JSON 결과 ② 결과마다 파일 지문·도구 버전·한계 기록(근거) ③ AI 연결

Q2. REA 코드는 어떻게 활용했나요?

REA 소스 코드를 고치지 않고, 완성된 REA 프로그램을 명령어로 불러서 썼습니다.

jins0001/rea (소스, TypeScript 35만 줄)
      │  같은 코드가 빌드되어 npm에 올라감
      ▼
npm install -g rea-agents@6.4.0   ← 노트북에 설치
      ▼
우리 스크립트(.ps1) ── rea 명령 ──▶ REA ──▶ JSON 결과
우리 Python(summarize.py) ◀── JSON 읽기 ──┘
      ▼
분석결과.md
REA 명령어디서꺼내 쓴 칸
inspect-managed-artifact2_분석하기파일 종류, 지문
inspect-managed-members2_분석하기signature(입출력), body.anchors(숫자·글자), call_edges(호출)
inspect-artifact4_도전파일 신분증
decompile --provider ghidra4_도전normalized_result(의사 코드)
비유: REA 소스는 "자동차 설계도", 설치한 REA는 "완성된 자동차". 설계도를 고친 게 아니라 차를 운전했습니다. 저장소 소스와 문서는 명령과 결과 모양을 확인하는 설명서로 읽었습니다.
